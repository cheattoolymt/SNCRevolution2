# SNCR2 改造ガイド（貢献の作法）

**この文書の目的**: SNCR2 に手を入れるときの判断基準と手順を示す。
とくに **「既に印刷された紙を読めなくしない」** ための規則を明文化する。

前提として [`ARCHITECTURE.md`](ARCHITECTURE.md) と
[`TESTING.md`](TESTING.md) を先に読んでください。

---

## 0. 最初に読むべき 1 行

> **紙は書き換えられません。**

ソフトウェアなら「次のバージョンで直す」ができます。
しかし SNCR2 のユーザーは、**すでに印刷した紙**を手元に持っています。
その紙のビット配置やヘッダの意味を変える変更は、
**過去に印刷されたすべてのカードを無価値にします**。

このプロジェクトで最も重い制約はこれです。性能・容量・コードの綺麗さより優先されます。

---

## 1. 変更の 3 分類

手を入れる前に、自分の変更がどれに当たるか判定してください。

### 🟢 A 類: 紙に影響しない変更

- コメント・ドキュメント・README
- UI の文言・見た目・エラーメッセージ
- **読み取り側だけ**の改善（サンプリング精度・検出アルゴリズム・速度）
- テストの追加

→ 比較的自由に触れます。ただし読み取り側の変更は
**既存の成功ケースを退行させない**ことを e2e で確認してください（§4）。

### 🟠 B 類: 新しい紙だけに影響する変更

- **新しい版の追加**（ver21 以降）
- 新しい ECC レベルの**追加**（既存番号は動かさない）
- 新しい `flags` bit の利用（予約 bit 2〜7）

→ 「新しいものだけに効かせ、既存には一切影響させない」設計が必須です。
`compat-selftest.js` がその証明になります。

### 🔴 C 類: 既存の紙を壊す変更

- 既存版の `cols` / `rows` の変更
- `LEGACY_COLS` のアライメント密度の変更
- 機能モジュールの配置・敷く順序の変更
- データセルの列挙順・充填順の変更
- マスク式・ペナルティ・フォーマット情報の符号化の変更
- ヘッダのバイトレイアウト・`flags` の意味の変更
- `ECC_LEVELS` の**番号**の並べ替え、`nsym` 算出式の変更
- `blockPlan` の割り当て規則の変更
- RS の体・生成多項式・パリティ位置の変更
- インターリーブの並べ替え規則の変更

→ **原則として禁止**です。どうしても必要な場合は §6 の手順を踏んでください。

一覧は [`FORMAT.md` §8](FORMAT.md#8-変更してはいけないもの後方互換) にもあります。

## 2. 絶対ルール

### 2-1. `compat-selftest.js` のゴールデン値を書き換えてはいけない

```bash
node test/compat-selftest.js
```

このテストは「ver1〜14 × ECC 0〜3 の 56 通りが、拡張前コミットとビット単位で同一」
であることを SHA256 で照合します。

**落ちたら、それは「既存の紙が読めなくなった」という意味です。**
期待値を実測値に合わせて更新して通すのは、
**問題を隠蔽して過去のユーザーを切り捨てる行為**です。実装側を直してください。

### 2-2. 出荷物の依存を増やさない

- 実行時依存はローカル同梱の `js/vendor/pako.min.js` のみ。
- CDN からの読み込みは **任意機能に限る**（PDF 入出力）。
  失敗時に必ずフォールバックすること（`window.__noJsPDF` / `window.__noPdfJs`）。
- npm パッケージを**出荷物**（`js/*`・`*.html`）に持ち込まない。
- テスト専用依存は「無くても動く」こと（`jpeg-js` → 自前コーデックへフォールバック）。

理由: `file://` で開くだけで動くこと、オフラインで完結することが本ツールの価値です。

### 2-3. 二値固定を崩さない

グレースケール・カラーの中間値を**データとして**使ってはいけません。
容量は増えますが、家庭用プリンタ・スキャナの階調再現性は信用できず、
「読めない紙」を大量生産することになります（§8 禁止事項）。

読み取り時に中間調を**判定材料として**使うのは問題ありません（適応しきい二値化）。

### 2-4. コアモジュールを DOM 依存にしない

`js/*.js` は DOM / Canvas に触らない純粋関数のままにしてください。
Canvas に触れるのは `creator.html`（描画）と `decoder.html`（画像入力）だけです。

理由: Node からテストできることが品質の担保になっています。
DOM に依存させると e2e が書けなくなり、実機で壊れるまで気づけません。

### 2-5. サイレントな誤復元を作らない

「たぶん読めた」を成功として返してはいけません。

- RS が能力超過したら `ok:false`（誤ったデータを `ok:true` で返さない）
- ページが欠けていたら `missingPages` を立て、成功と報告しない
- 圧縮の展開後は元の長さと一致するか自己検証する

理由: 復元したファイルが**静かに壊れている**のは、読めないことより有害です。

### 2-6. 読み取り側の総当たりを削らない

`decodeAnyVersion` の既定（`invert` 両方 × 全版 × `useAlignment` 両方）は、
「読めない紙を作らない」ための安全網です。速度のために既定を削らないでください。

速度改善は **候補の並べ替え**（`estimateGridPitch`）のように、
**候補集合を変えない**方法で行ってください。

## 3. 変更してよい / 変更しにくい場所（危険度マップ）

| 場所 | 危険度 | 変更時に必須のテスト |
|---|---|---|
| `docs/*` `README.md` UI 文言 | 🟢 小 | — |
| `decode-core.js`（サンプリング・検出） | 🟡 中 | e2e + align + message |
| `geometry.js` | 🟡 中 | e2e + align |
| `compress.js` | 🟡 中 | 手動確認（e2e はカバーしない） |
| `creator.html` の `renderPage` | 🟠 大 | e2e（箱定数と厳密一致が必要） |
| `qr-mask.js` | 🟠 大 | core + **compat** |
| `qr-interleave.js` | 🟠 大 | core + **compat** |
| `qr-version.js`（新版の追加） | 🟠 大 | design + **compat** |
| `qr-align.js` の密度体系 | 🔴 極大 | design + **compat** + align |
| `qr-version.js` の `VERSION_COLS_STD` | 🔴 極大 | **原則変更禁止** |
| `qr-header.js` のレイアウト | 🔴 極大 | core + **compat** + message |
| `qr-core.js` の配置・充填順 | 🔴 極大 | 全部 |

## 4. 標準的な作業手順

### 4-1. 事前に基準を取る

改造前に**必ず**現状の結果を保存してください。「元々どうだったか」が
分からないと退行を検出できません。

```bash
node test/design-selftest.js > /tmp/before-design.txt
node test/core-selftest.js   > /tmp/before-core.txt
node test/compat-selftest.js > /tmp/before-compat.txt
node test/e2e-selftest.js    > /tmp/before-e2e.txt
```

### 4-2. 変更する

- 該当ファイル冒頭のドキュメントコメントを**一緒に更新**する。
  「なぜそうしたか」を書く（何をしたかはコードを読めば分かります）。
- 既存の設計判断に反する変更をするときは、
  **元の判断の理由を読んでから**（コメントに書いてあります）。

### 4-3. 検証する

[`TESTING.md` §9 の早見表](TESTING.md#9-変更内容別実行すべきテスト早見表)に従って
テストを走らせ、`before` と差分を取ります。

```bash
node test/e2e-selftest.js > /tmp/after-e2e.txt
diff /tmp/before-e2e.txt /tmp/after-e2e.txt
```

**`PASS` が `FAIL` になっていないこと**が最低条件です。
数値（訂正セル数 `corr` など）の変化があれば、それが説明できるか確認してください。

### 4-4. コミットする

- 1 コミット 1 目的。
- Conventional Commits 形式: `type(scope): 説明`
  - `feat` / `fix` / `docs` / `test` / `refactor` / `perf` / `chore`
  - 例: `fix(decode): 適応しきいの局所窓が小さすぎる問題を修正`
- 本文には **「なぜ」** と **「どう検証したか」** を書く。
- 🔴 C 類の変更を含む場合は、コミットメッセージに
  **後方互換への影響と、そう判断した根拠**を明記する。

### 4-5. PR を出す

PR 説明に次を含めてください。

```markdown
## 変更の分類
A 類（紙に影響しない） / B 類（新しい紙だけ） / C 類（既存の紙に影響）

## 何を変えたか / なぜ

## 後方互換
- [ ] `node test/compat-selftest.js` が PASS（ゴールデン値は未変更）
- 既存 ver1〜14 のカードへの影響: なし／あり（詳細）

## 実行したテスト
- [ ] design  - [ ] core  - [ ] align
- [ ] message - [ ] compat - [ ] e2e
（結果の抜粋を貼る）

## 出荷物の依存
- [ ] 増やしていない（js/* と *.html は依存ゼロを維持）
```

## 5. コーディングスタイル

コードそのものより、**コメントの質**を重視するプロジェクトです。

### 5-1. ファイル冒頭のドキュメントコメント

各ファイルの冒頭に、次を書いてください（既存ファイルの形式を踏襲）。

```js
/*
 * SuperNaidesuCardRevolution II (SNCR2) — ファイル名
 * ==================================================================
 * このファイルの責務（1〜3 行）
 *
 * ── 移植元 ─────────────────────────────────────────────────────
 *   （nayuki / 旧 cardloader から持ってきた場合は必ず明記）
 *
 * ── 入出力 ─────────────────────────────────────────────────────
 *
 * ── 依存 ───────────────────────────────────────────────────────
 *
 * このファイルは DOM 非依存の純粋関数のみ。
 * ================================================================== */
```

### 5-2. 「なぜ」を書く

このプロジェクトのコメントは異様に長いですが、それは意図的です。

```js
// ❌ 悪い例（コードを読めば分かる）
// inset を計算する
const insetX = Math.min(0.5, rect.w * 0.06);

// ✅ 良い例（なぜその値なのかを残す）
// 隣接セルの滲み・重なりを避ける「内側詰め」は、従来 0.5px 固定だったが
// 高密度版では 1 セルが 6〜8px しかなく、0.5px 詰め（両側で 1px）が
// セル面積の 25% を削ってしまう。詰め量をセル寸法に比例させることで、
// 低密度版は従来と同じ見た目を保ちつつ高密度版では黒セルの面積を確保する。
```

とくに次は必ず理由を書いてください。

- **採用しなかった案とその理由**（例: 「2 ページ目以降のヘッダ削除」を
  採用しなかった判断が `card-format.js` に長く書かれています）
- **マジックナンバーの根拠**（どの実測・どの式から来たのか）
- **後方互換のための不自然な構造**（`byte[7]` 転用など）
- **実機フィードバックへの対応**（何が壊れて、なぜその対策なのか）

### 5-3. 実装規約

- `'use strict';` を付ける。
- UMD 形（ブラウザのグローバル + Node の `module.exports`）を維持する。
- ES5〜ES2017 相当に留める（古いブラウザでも `file://` で動くように）。
- 外部から呼ばれる関数は、返り値の形を**コメントで明示**する。

### 5-4. 数値を文書に書くときは実行して確認する

docs に容量や座標を書くときは、必ず `node -e` などで実測してから書いてください。
古い数値が残ると、後から読む人が実装をバグと誤認します。

```bash
node -e "const CF=require('./js/card-format.js'); console.log(CF.netCapacity(CF.getProfile(20),3));"
```

## 6. どうしても C 類の変更が必要なとき

「既存の紙を壊す」変更が本当に避けられない場合の手順です。

1. **本当に避けられないか再検討する。**
   多くの場合、「新しい版・新しい ECC レベル・予約 bit の利用」という
   B 類の形に落とし込めます（`byte[7]` 転用がその実例です）。
2. **新旧を共存させる。** 旧仕様を読める経路を残したまま、
   新仕様を追加する（読み取り側で両方試す）。
3. **判別手段を用意する。** 紙を見て・読んで、どちらの仕様かが分かること。
   紙に情報を増やせないなら、`flags` の予約 bit を使う。
4. **`compat-selftest.js` を拡張する。** 旧仕様のゴールデン値を**残したまま**、
   新仕様のゴールデン値を追加する。旧値は消さない。
5. **移行方法を文書化する。** ユーザーが「持っている紙をどうすればよいか」を
   README とリリースノートに書く。
6. **それでも旧仕様を読めなくする場合は、メジャーバージョンを上げ、
   影響を最上位に明記する。**

## 7. よくある失敗パターン

過去に実際に起きた（あるいは起きかけた）失敗です。

| 失敗 | 何が起きたか | 教訓 |
|---|---|---|
| 固定しきい 128 での二値化 | ドットゲインで白背景が 128 を割り、セルの約半数が反転して RS 能力を超過。実機で復元不能 | 実機の劣化は「局所」ではなく「全面一律」で来る。適応しきいにする |
| `reason` の設定漏れ | 「版は確定・本文だけ失敗」を「版すら不明」と同じ文言で表示し、利用者が原因を誤認 | 失敗の**種類**を呼び出し側が区別できるようにする |
| 真値の取り方を間違えた検証 | たわみで動いた真のパターン中心をクリーン座標と比較し、健全な検出をバグと誤認（偽アラーム） | 期待値の導出根拠を残す。順写像で真値を計算する |
| PDF を 300dpi で固定ラスタライズ | Creator が 600dpi で埋め込んだのに読み側で 300dpi へ落とし、拡張版が復号不能 | 生成側と読み取り側の解像度前提を一致させる |
| 満載運用の過信 | ver14 を正味ギリギリまで詰め、実機でマージンが枯れた | 訂正上限と実測誤り率が拮抗する領域を避ける運用ガイドを示す |
| ヘッダ削除による容量稼ぎ（**却下**） | 実測 0.09% しか効かないのに「1 枚汚損で全滅」を招く設計 | 容量のために堅牢性を売らない |

## 8. 質問・判断に迷ったとき

判断基準の優先順位は次のとおりです。上が強い。

1. **既に印刷された紙が読めること**（後方互換）
2. **サイレントな誤復元をしないこと**（壊れたデータを成功と言わない）
3. **オフライン・依存ゼロで動くこと**
4. **読み取り成功率**
5. **容量**
6. **速度**
7. **コードの綺麗さ**

「容量を増やすためにアライメントを削る」ような提案は、
4 と 5 のトレードオフを 1 に触れずに解決できるかで判断します
（実例: アライメント密度を `∝ 1/√cellPx` にすることで、
歪み補正能力を物理的に保ったまま個数を減らし、`LEGACY_COLS` は凍結した）。
