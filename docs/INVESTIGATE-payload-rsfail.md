# 調査: 「verX 確定・本文（payload）RS 失敗」の根本原因

## 1. 再現条件

`decodeAnyVersion` が `reason='payload-rs-fail'`（＝ヘッダ RS 完全成功・本文 RS
失敗）を返す帯域を、実機フィードバックの劣化モデルで再現した。

| 項目 | 値 |
|------|-----|
| 版 / ECC | ver14 / ECC 高（ecc3） |
| データ | 正味容量満載（payloadLen=7190B） |
| 劣化 | `dotGain(growPx:3, blackFloor:10, whiteCeil:70)` → 本物 JPEG `q=12` |
| 結果 | ヘッダ RS 完全成功（version=14 確定）／本文 RS 失敗 |

## 2. 計測結果（ブロック別失敗調査）

### 2-1. モジュール（セル bit）層

```
反転セル: 1910/90000 = 2.12%
```

四隅検出・アライメント制御点メッシュ・適応しきい二値化を通した **後** のセル反転率は
わずか **2.12%**。つまりサンプリング自体は概ね健全で、「大量反転で全滅」という
§10-4 のドットゲイン破綻（固定しきい 128 時代の flips≈49%）とは **別物** である。

### 2-2. RS ブロック層

```
gross=10466B, ブロック数=42, nsym/block=78, 1ブロック訂正能力 t=39 byte（ブロック長 250）
総 byte 誤り=1643, 平均/block=39.1, 最大=50, 最小=23
RS 失敗ブロック=19/42, 能力超過(err>t)=19/42
誤り上位10ブロック: 50,48,48,47,47,46,46,45,45,44
```

- 1 ブロックの訂正能力は **t = nsym/2 = 39 byte**。
- 実測のブロック平均誤りは **39.1 byte** ＝ **ちょうど訂正上限の上に乗っている**。
- **19/42 ブロック（≈45%）が t を僅かに超過**（40〜50 byte）して失敗している。
  超過量は最大でも 50-39=11 byte 程度で、「桁違いに壊れている」わけではない。

### 2-3. 一様 vs バースト

```
ブロック誤り数 平均=39.1, 標準偏差=6.2, 変動係数 CV=0.158
```

ブロック間の誤り数のばらつきは小さい（CV≈0.16）。**誤りは特定領域に固まった
バーストではなく、盤面全体にほぼ一様に分布**している。

## 3. 原因の切り分け（結論）

### これは「実装バグ」ではない

- サンプリング（四隅・メッシュ・適応しきい）は 2.12% flips と健全に動作。
- インターリーブ／デインターリーブは `test/core-selftest.js`（最大版で 1310B
  連続破損の復元）と本ツールの突き合わせで整合を確認済み。取り違えは無い。
- ヘッダ RS（nsym=6・18B・別ブロック保護）は完全成功しており、RS デコーダ自体も
  正しく動いている。

### これは「劣化が RS 能力を（僅かに）超えている」＝設計マージンの問題

根本原因は次の 2 段の増幅にある。

1. **bit→byte 増幅**: モジュール反転は 2.12% と低いが、RS は **byte 単位**で誤りを
   数える。1 byte = 8 セルなので、1 セルでも反転すればその byte 全体が「誤り」に
   なる。反転がほぼ独立・一様なら byte 誤り率は概ね
   `1-(1-0.0212)^8 ≈ 15.7%` に増幅される。実測の平均 byte 誤り率
   **≈15.6%**（39.1/250）とほぼ一致する。
2. **RS 上限との拮抗**: ECC 高の 1 ブロック訂正率は `t/blockLen = 39/250 = 15.6%`。
   増幅後の byte 誤り率 15.6% が **RS 上限 15.6% とちょうど拮抗** するため、
   統計的なばらつき（CV=0.16）で上振れしたブロックだけが次々に能力超過し、
   結果として約半数のブロックが失敗する。

一様分布なので **インターリーブ（バースト分散）では救えない**。効くのは
「ECC 余裕を増やす」か「モジュール反転率そのものを下げる」かのいずれか。

## 4. 対策の方向性（次工程の候補・本 PR では未実装）

本 PR は **調査（原因の数値的確定）まで** をスコープとする。修正は反転や退行の
リスクがあるため、下記候補を別途検証してから入れる。

1. **満載時に ECC 高を過信しない運用ガイド**: 平均 byte 誤り率 15.6% は ECC 高の
   訂正上限そのもの。ver14 を正味容量ギリギリまで満載すると、実機ドットゲイン+
   低品質 JPEG でマージンが枯渇する。`creator.html` で「満載 ver14 は劣化耐性が
   薄い」旨を促し、1 段低い版＋複数ページ or 余白を残す運用を推奨する。
2. **モジュール反転率の低減（サンプリング改善）**: 現状はセル中心近傍の平均→
   適応しきいで 1 値判定。セル内を複数点サブサンプルして多数決する、あるいは
   セル面積に対するサンプリング半径 `samplingRadius` を見直すことで、境界セルの
   反転（2.12% の主因）を数十%削れる可能性がある。§10-9 の margin 同様、
   クリーン/低密度/他劣化を退行させないことを e2e 掃引で確認したうえで入れる。
3. **ECC 段のオーバーヘッド再配分**: ブロック長 250・t=39 は「上限ちょうど」で
   運用マージンが 0。実機分布（平均+2σ ≒ 39.1+12.4）を吸収するには、満載時に
   実効 ECC を +5〜10% 引き上げる（＝正味容量をその分削る）余地を検討する。
