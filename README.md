# SuperNaidesuCardRevolution II (SNCR2)

**ファイルを「紙」に保存するツールです。**
A4 用紙 1 枚に最大 **約 20KB** のデータを白黒の点々として印刷し、
その紙をスキャンすると **元のファイルがそのまま戻ってきます**。

_クラウド？いらないです。数十キロバイトを、数円で。
（※紙代とインク料金、印刷一回の電気代のみ換算）_

- **サーバー不要**・**インストール不要**・**通信ゼロ**。HTML を開くだけで動きます。
- 入れたデータが外に出ることはありません（すべてブラウザの中だけで処理されます）。
- 紙は電源も互換性も要りません。10 年後のパソコンでも、このツールがあれば読めます。

## 3 分で試す

### 1. ダウンロードする

```bash
git clone https://github.com/cheattoolymt/SNCRevolution2.git
cd SNCRevolution2
```

（ZIP ダウンロードして展開するだけでも構いません。ビルド作業は一切ありません。）

### 2. `index.html` をブラウザで開く

ダブルクリックで開けます。サーバーを立てる必要はありません。
※`file://` のままで動作します。

### 3. カードを作る（印刷する）

1. `🖨️ カードを作る (Creator)` を押す
2. 保存したいファイルを選ぶ（テキスト・画像・zip、何でも可）
3. **密度（版）** と **誤り訂正（ECC）** を選ぶ
   → まずは初期値の **ver14 / ECC 高（約30%）** のままで OK
4. `④ カード画像を生成` → `PNG を保存` または `PDF を保存`
5. **モノクロ（白黒二値）で等倍印刷**する
   （「用紙に合わせて拡大縮小」は **OFF**。100% で印刷してください）

### 4. カードを読む（復元する）

1. 印刷した紙を **スキャナで 300dpi 以上** で取り込む
2. `🔍 カードを読む (Decoder)` を開く
3. スキャン画像（複数ページなら全部まとめて）をドロップ
4. `復元する` → `復元ファイルを保存`

これで元のファイルが戻ります。

> **最初の 1 回は「印刷せずに」試すのが確実です。**
> Creator で生成した PNG をそのまま Decoder にドロップすると、
> 印刷・スキャンの品質問題を切り分けたうえで動作確認できます。

## これは何？

旧 [`naidesu-cardloader`](https://github.com/cheattoolymt/naidesu-cardloader) の後継です。
任意のバイナリを紙に印刷し、印刷 → スキャンで復元する静的 HTML/JS 完結ツールです。

QR コードのコア技術（**マスク最適化**・**アライメントパターンによる歪み耐性**）を
移植し、**同じセルサイズ・同じセル数でも読み取り成功率そのものを底上げする**ことを
目的としています。二値（白黒）固定です。

### できること / できないこと

| | |
|---|---|
| ✅ できる | 任意のバイナリ（テキスト・画像・zip・鍵ファイル等）を A4 に焼く |
| ✅ できる | A4 1 枚で最大 約20KB（ECC 20% を付けても 約16KB） |
| ✅ できる | 大きいファイルの自動複数ページ分割・スキャン画像からの自動結合 |
| ✅ できる | 自動圧縮（deflate / gzip / brotli / 日本語辞書から最良を自動選択・可逆） |
| ✅ できる | 汚れ・かすれ・傾き・たわみからの誤り訂正（Reed–Solomon） |
| ❌ できない | メガバイト級のバックアップ（紙が何百枚も必要になります） |
| ❌ できない | カラー/グレースケール印刷（**二値固定**。互換性が壊れます） |
| ⚠️ 非推奨 | スマホカメラでの撮影読み取り（動きますが失敗しやすい → 下記） |

### 用途の例

- パスフレーズ・リカバリーキー・秘密鍵の紙バックアップ（オフライン保管）
- 設定ファイル・証明書・小さな台帳のオフライン退避
- 「ネットに載せたくないが手元に残したい」小さいデータの長期保存

## 必要なもの（重要）

| 必要なもの | 条件 |
|---|---|
| ブラウザ | モダンブラウザ（Chrome / Edge / Firefox / Safari の最近のもの） |
| プリンタ | モノクロ印刷ができるもの。**等倍（100%）印刷**必須 |
| スキャナ | **300dpi 以上**（拡張密度 ver15〜20 を使うなら **600dpi 以上**） |

### 📷 読み取り機材の想定

- **推奨: スキャナ**（正面・等倍・平面固定）
- **非推奨: スマートフォンカメラ撮影** — 動作はしますが、0.7mm 級の高密度セルでは
  傾き・光量ムラ・手ブレで失敗しやすいです。

QR コードは「雑なカメラ撮影でも読める」ように設計されていますが、本ツールは
**高密度セルで容量を稼ぐ**ためスキャナ前提で密度・ECC を設計しています
（カメラでも一応動く保険として射影変換・適応サンプリングは残してあります）。

### 解像度はティア（版の帯）で変わります

| ティア | バージョン | セル | 印刷/スキャン |
|--------|-----------|------|---------------|
| 標準   | ver1〜14  | 0.73〜3.04mm | **300dpi** 以上 |
| 拡張   | ver15〜20 | 0.52〜0.69mm | **600dpi** 以上 |

拡張ティアを選ぶと Creator が警告を出し、生成画像を自動で 600dpi 相当へ
拡大して描画します。**300dpi のプリンタ／スキャナしか無い場合は ver14 以下**を
選んでください。

## 容量（A4 1 枚あたり）

グロス最大 **約 20KB**。ECC を付けた実効容量は次のとおり（KB=1024B）:

| ver | cols×rows | セル | 必要dpi | ovh% | ECCなし | 5% | 10% | 20% | 30% | 40% |
|-----|-----------|------|---------|------|--------|-----|-----|-----|-----|-----|
| 14  | 250×360 | 0.73mm | 300 | 6.8% | 10.2KB | 9.6KB | 9.2KB | 8.1KB | 7.0KB | 6.0KB |
| 15  | 265×381 | 0.69mm | 300 | 5.4% | 11.6KB | 11.0KB | 10.5KB | 9.3KB | 8.1KB | 7.0KB |
| 17  | 296×426 | 0.62mm | 600 | 4.6% | 14.7KB | 13.9KB | 13.2KB | 11.7KB | 10.2KB | 8.8KB |
| 20  | 348×501 | 0.52mm | 600 | 4.0% | **20.4KB** | 19.3KB | **18.3KB** | **16.2KB** | 14.2KB | 12.2KB |

つまり **ECC 20%（中）を付けたまま 16KB**、**ECC 10%（低）で 18KB**、
無保護なら 20KB が A4 1 枚に載ります（従来の上限は ver14 の 10.2KB）。
**全 20 版 × 全 8 段階 ECC の正確な表**は `node test/design-selftest.js` が出力します。

> ⚠️ **満載運用の注意**: ver14/ver20 を正味容量ギリギリまで詰めると、実機の
> ドットゲイン（インク滲み）＋低品質 JPEG で誤り訂正の余裕が枯れます。
> 大事なデータは **1 段低い版 + 複数ページ**、または **ECC を高め**にしてください。
> 詳しい数値的根拠は [`docs/INVESTIGATE-payload-rsfail.md`](docs/INVESTIGATE-payload-rsfail.md)。

### 容量を上げるために行った 4 つの変更

1. **バージョン拡張（ver15〜20）** — 同じデータ箱（2152×3096px 固定）をさらに
   細分します。0.7mm を割るため下限を 0.50mm へ緩めましたが、**力技の縮小ではありません**:
   拡張ティアは印刷/スキャンを 600dpi にする前提なので、1 セルあたり 11.8px 以上を
   確保します（300dpi・0.7mm の 8.27px より **むしろ高精細**）。`creator.html` は
   拡張版を選ぶと canvas を自動で 600dpi 相当へ拡大して描画します。
2. **オーバーヘッド削減（6.7〜13.8% → 4.0%）** — (a) 実体の無い「バージョン情報
   36 セル」をモデルから削除（SNCR2 は版数を盤面に持たず、ヘッダ byte[2] と
   全版試し読みで確定するので不要でした）、(b) アライメント密度を「セル数一定」から
   **「bilinear 補間残差が一定」** になる法則（間隔 ∝ √セル px）へ変更。歪み補正
   能力を物理的に保ったまま個数を減らしました（ver20 換算で 429 → 244 個）。
   **既存 ver1〜14 のレイアウトは 1bit も変えていません**（後方互換）。
3. **ECC 率の細分化（4 → 8 段階）** — なし / 5% / 10% / 15% / 20% / 25% / 30% / 40%。
   「なし」と「10%」の間が飛びすぎる問題を 5% で埋めました。ヘッダを 1byte も
   増やさずに実現するため、**必ず 0 になる byte[7]**（totalFileLen BE32 の最上位
   バイト。物理上限は 255 ページ×約 20KB ≒ 5MiB なので常に 0）を flags へ転用しています。
   既存カードは `byte[7]==0` ＝ flags 無しと解釈され、そのまま読めます。
4. **複数ページの効率化** — 当初案の「2 ページ目以降のヘッダ削除」は実測すると
   **0.09% しか効かない**のに、ページ順序・版・ECC を 1 ページ目に依存させて
   「1 枚汚損で全滅」という堅牢性の後退を招くため採用しませんでした。代わりに桁違いに
   大きい無駄＝**最終ページのパディング**を潰しました。ver20/ECC高 で 50B の端数を
   焼くと従来は 14,504B 枠を丸ごと使っていましたが、最終ページだけ残量が収まる最小版
   （この例では ver1）へ自動縮小します。紙が減るうえ、最終ページのセルが 0.52mm →
   3.04mm と 6 倍大きくなり **読み取りはむしろ頑丈になります**。

> **読み取り速度**: 版が 20 に増えると全版試し読みが重くなる（実測 18 秒）ため、
> `decode-core.js` に**セルピッチのスペクトル推定**を追加し、正解の版を最初に
> 試すよう候補を並べ替えました（18 秒 → 約 1 秒）。推定が外れても全版フォールバックは
> 残るので、正しさは一切犠牲にしていません。

## 困ったときは（トラブルシュート）

| 症状 | 原因の候補と対処 |
|---|---|
| 「四隅マーカーを検出できません」 | 紙の四隅が見切れている／傾きすぎ／コントラスト不足。**紙全面**が入るように、正面・平面固定で再スキャン。 |
| 「ver 不明・検出失敗」 | スキャン解像度不足が最有力。**拡張密度（ver15〜20）は 600dpi 必須**。フチなし縮小印刷になっていないかも確認。 |
| 「verX 確定・本文の誤り訂正に失敗」 | 版までは読めており、劣化が誤り訂正の限界を超えています。再スキャン（解像度を上げる／モノクロで取り込む）、または **ECC を高くして作り直し**。 |
| 「ページが足りません」 | 複数ページのうち一部しか読み込んでいません。**全ページの画像をまとめて**選択してください。 |
| PDF が読み込めない | PDF 入出力は任意機能（CDN の jsPDF / PDF.js を使用）。オフラインや CDN ブロック環境では **PNG を使ってください**（PNG 経路は完全ローカルで動きます）。 |
| 印刷物が薄い／太い | プリンタのトナー濃度・用紙設定を調整。「インク節約」「ドラフト」モードは OFF。 |
| 全体的に読めない | **等倍（100%）印刷**になっているか、**カラー/グレースケールになっていないか**を確認。 |

### §8 禁止事項・非機能要件（遵守事項）

実装は指示書 §8 の制約を全ファイルで満たしています:

- **多値化・カラー化は禁止（二値固定）**: 描画は `creator.html` の `renderPage`
  で黒セルのみ塗り、読み取りは `card-format.otsuThreshold`（大津法）で二値化します。
  グレースケール/カラーの中間値をデータに用いる箇所は存在しません。
- **完全ブラウザ完結・静的 HTML/JS のみ**: サーバ不要・外部送信なし。すべての
  コアモジュールは DOM 非依存の純粋関数（Node からも `require` できる UMD 形）で、
  Canvas/DOM に触れるのは `creator.html`（描画）と `decoder.html`（画像入力）のみです。
- **外部依存は最小限**: 実行時依存はローカル同梱の `js/vendor/pako.min.js` のみ
  （圧縮）。`creator.html` の jsPDF / `decoder.html` の PDF.js は PDF 入出力の**任意**
  機能で、読み込み失敗時は PNG 経路へ自動フォールバックします
  （`window.__noJsPDF` / `window.__noPdfJs`）。
- **改造しやすさ最優先**: nayuki 方式のドキュメントコメント密度を踏襲し、各ファイル
  冒頭に責務・入出力・指示書該当章を明記しています。
